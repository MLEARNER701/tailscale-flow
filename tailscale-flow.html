How it is measured, and the limits
  • measuredBytes: the peer's RxBytes/TxBytes from tailscale status --json, read every second; the rate is the difference over time. WireGuard bytes for this one peer only.
  • measuredPackets: tailscaled_inbound/outbound_packets_total from tailscale metrics print (summed over paths). These count every peer, so the page scales them by this peer's share of bytes in the same second (orx/otx are the other peers' bytes). Other peers' bytes during this trace: —.
  • measuredPackets on the OS tunnel interface (netstat -ib, utun) are shown in the table only. Traffic that tailscaled handles itself, such as tailscale serve, never crosses utun, so utun counts can be far below the peer byte counts.
  • measuredRound trip: tailscale ping -c 1, re-sent as soon as the previous answer arrives (at most once per --ping-every). SRTT and RTTVAR use the RFC 6298 constants (α 1/8, β 1/4); lost probes do not update the estimate.
  • measuredPath: if the peer has no CurAddr but has a Relay, traffic goes through a DERP relay; with a CurAddr it is a direct connection (LAN or WAN). The via of each ping answer is recorded too.
  • inferredOver DERP, packets go to the receiver's home DERP region. So "sent" is drawn through the peer's home (—) and "received" through this machine's home (—). The reverse direction is not observed directly.
  • designDot density, speed and size are log-scaled metaphors: one dot is not exactly one packet. Dots move in real time; the playback speed only changes how fast the values change.
  • Public IPs and tailnet IPs are never recorded. A direct endpoint is reduced to LAN or WAN.
— Collector: flow_collector.py (read-only, Python standard library only). For live data run flow_collector.py serve and open this page with ?src= pointing at its flow.json.
